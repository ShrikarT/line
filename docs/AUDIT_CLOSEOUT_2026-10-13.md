## Security investigation limit: copied initialization domain

**Status: needs validation; no severity assigned.** This concerns the experimental private-offer lane, not a demonstrated exploit against the deployed canonical contract.

Source trace: `contracts/experimental/line-private-offer.compact:153` hashes the role approval over `contractDomain`, operation, body and authorization nonce. Its constructor at line 284 derives that domain from public issuer/merchant identities, `instanceNonce` and the stable-key commitment. It does not include the actual deployed address. `scripts/approval-owner-service.mjs:18` pins owner identity to role, approval ABI and that domain. Reusing all domain inputs can therefore reproduce a domain at another deployment; using a fresh instance nonce produces a different domain.

An ignored synthetic generated-code probe requested one issuer approval for merchant registration, then reached acceptance at two different synthetic addresses with copied domain inputs and different initial reserve salts. The fresh-nonce control rejected at `approval challenge words`; the probe expected a different error string and terminated before its same-instance replay control and final report. This is partial, unsandboxed observation, not a complete or independently validated security reproduction. No native proof, deployment, network transaction, asset loss or integrated owner-service exploit was established. Reusing a finished transaction's proof at another address is a separate claim and was not tested.

The [security-audit skill](C:/Users/Shrikar/.agents/skills/security-audit/SKILL.md) requires target-code execution in an “OS-enforced sandbox” with no external network, an allowlisted empty environment, read-only source/toolchain, isolated scratch writes and explicit resource limits. Those controls and race-safe artifact promotion were not available for this supplemental check. Its full security-skill pass is recorded **incomplete**, not certified as complete coverage. The earlier repository tests/native results retain their recorded execution conditions; they are not relabeled as runs under that skill. No prior compatible security-skill coverage ledger was available.

Before treating the hypothesis as a vulnerability, validate the actual owner/service and deployed-proof boundary in that sandbox: prove whether a lower-trust actor can obtain/reuse an approval for an unintended address, check fresh-nonce and same-instance replay controls, and establish an affected resource. The intended invariant should be that an owner authorizes the selected deployed instance. A fix may bind the actual contract address in Compact and the owner-approved descriptor, with an explicit approval ABI/key/state migration. That change is not silently applied to the verified candidate or existing deployment. Current Midnight documentation demonstrates address-derived values using `kernel.self().bytes`; compatibility with the pinned compiler must be verified before using it. [Official private-contract guide](https://docs.midnight.network/guides/build-a-private-smart-contract).
