# Native recovery evaluation and compiler regression checks

The restored financial fixture passes native ZKIR evaluation for six lifecycle candidates: funding, consent posting/acceptance, supplier quote, draw and redemption. It reloads financial candidates across 20 storage subprocess invocations. Each call rejects a corrupted communications commitment and an extra private transcript value: twelve negative controls in total. [Fingerprint-bound evaluation report](private-signed-2026-10-11-evidence/financial-recovery-native-evaluation.json).

The SDK supplies real serialized preimages to `midnight-transient-crypto` 2.1.1's `ProofPreimage.check` over the exact compiled binary IR, through the pinned `midnight-zkir` 2.1.1 interpreter. Private preimages travel over stdin and are never written to evidence files. The report retains pass/failure categories and statement block counts, with source, generated executable, IR/verifier, helper, native executable and dependency-lock fingerprints. The provider deliberately stops before returning a proof. These are witness/constraint checks, not cryptographic proofs or ledger acceptance.

This new execution does not reproduce the exact ephemeral values from the earlier HTTP 400 attempt. It establishes that the fresh restored candidates satisfy the native interpreter; it does not identify the earlier failure's cause. Separate native proof verification, complete coordinator reconstruction, all-role custody, network finality and settlement remain separate requirements.

The [official compiler advisory](https://github.com/LFDT-Minokawa/compact/security/advisories/GHSA-3p6x-5vpx-wwpj) describes a conditional and unconditional narrowing of the same wider witness whose common-subexpression elimination could remove a required range check. Its affected-version metadata includes 0.31.1, while its remediation text recommends 0.31.1. This inconsistency prevents relying on the version string alone. Three freshly compiled probes on the project's pinned 0.31.1 compiler retain an unconditional eight-bit range constraint on that wider witness. [Probe results](private-signed-2026-10-11-evidence/compiler-cse-range-probes.json).

One unconditional range gate is sufficient for this trigger. An initial harness demanded two and failed; inspection showed its criterion was overly strict, and the corrected probe checks the gate's actual target and unconditional placement in a linear instruction stream. CI now runs these probes. They are temporary test contracts outside Line's twelve-circuit ABI. This is a narrow structural regression check, not a general compiler soundness proof, malicious proof test or verification of deployed keys. No canonical contract or managed artifact was changed.

Reproduce evaluation after building the checker:

```text
npm run proof:preimage:build
npm run finance:preimage -- <full-private-offer-managed-dir> <fresh-recovery-managed-dir>
npm run compact:range:check
```

The separate optional Docker-free proving backend uses the same pinned native libraries, the exact full keys and `ProofPreimage.prove`, including its built-in proof self-verification. It accepts binding overrides through a private stdin envelope, emits only tagged public proof bytes, and fetches checked public CRS parameters from the official source into a run-specific cache. The existing recovery proof driver still requires independent Rust transaction verification before confirming a checkpoint. Build with `npm run proof:local:build`, then run `npm run proof:finance -- <full-private-offer-managed-dir> <fresh-recovery-managed-dir> --native-local`. A successful build or interpreter evaluation does not establish that this backend completed a proof run; consult its separate final report.

The first native attempts stopped during funding with a process failure after key material loaded. The bounded diagnostic records exit code `3221225725` (`0xC00000FD`), which Microsoft identifies as [stack overflow](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/debugging-a-stack-overflow). This is a separate failure from the earlier Docker HTTP 400. The helper now uses a 64 MiB owned worker stack and 16 MiB Tokio worker stacks; global process defaults are unchanged. [Historical attempt metadata](private-signed-2026-10-11-evidence/financial-recovery-local-prover-attempts.json). The subsequent run completes six calls with separate cryptographic verification and one corrupted draw rejection. Its [pre-ACL-fix report](private-signed-2026-10-11-evidence/financial-recovery-native-proof-before-acl.json) retains the earlier storage helper's exact fingerprint; it is not relabeled as verification of later storage code.

The subsequent Windows regression found 22 failures caused by `Get-Acl` module autoload under inherited PowerShell module paths; 471/493 tests passed in that run. The store now reads the same access rules through the supported [.NET directory ACL API](https://learn.microsoft.com/en-us/dotnet/api/system.io.directory.getaccesscontrol?view=netframework-4.8.1) in its Windows PowerShell child, with terminating errors. It still grants only owner/SYSTEM access and rejects other explicit entries. Both new Windows tests pass: unavailable module discovery does not block valid storage, and an explicit Everyone reader still rejects. The full revised Windows suite passes **495/495 tests across 60 suites**. CI includes these two controls in a dedicated Windows job; Linux reports them as skips. No machine-wide module configuration was changed. As with the earlier shared-store change, checkout snapshots bound to the old implementation require explicit migration.

The first ACL-fix revision was then freshly compiled, evaluated and proved again. Its [native report published at `cfbc939`](private-signed-2026-10-11-evidence/financial-recovery-native-proof.json) completes six calls across five names, verifies every transaction in a separate Rust process, rejects one decodable corrupted draw, restores financial candidates through all 20 storage invocations and passes two agent restarts. Proving totals 257,870 ms. This closes local proof completion for that exact fixture. It does not certify all twelve recovery paths, whole-coordinator restart, independent operators, rollback resistance, live fees/finality/assets or historical privacy. The earlier HTTP 400 cause remains unknown; the new run uses fresh ephemeral values and a different proving backend.

Both `cfbc939` workflow runs failed their new Windows job: the unrelated-reader control passed, but valid storage with unavailable module discovery failed. The Linux verification job passed 493 tests with two platform skips, 20 browser checks and the compiler probes. [Push run](https://github.com/ShrikarT/line/actions/runs/38218062378), [PR run](https://github.com/ShrikarT/line/actions/runs/38218065774). The first ACL fix retained PowerShell's `.Access` projection. The follow-up uses the actual [.NET `GetAccessRules` method](https://learn.microsoft.com/dotnet/api/system.security.accesscontrol.commonobjectsecurity.getaccessrules), includes explicit and inherited rules, and requests SID objects directly. Both Windows controls pass locally. This changes only rule enumeration, not the access policy; fresh remote verification is required. Native reports retain their earlier helper fingerprints and are not relabeled as cryptographic verification of this later lookup change.

The enumeration revision passes the full 495-test/60-suite local regression, fresh compiled financial recovery and six native evaluations with twelve corruption rejections. The public generated and evaluation reports now pin that exact revision. The six-call cryptographic report continues to pin `cfbc939`'s earlier rule lookup; no extra cryptographic run is claimed for this API-only follow-up.

The subsequent `0cbba45` hosted Windows diagnostic identifies `ACL_POLICY_REJECTION` for the positive fixture, rather than a command failure. The test's temp directory was not established with the required owner/SYSTEM-only rules. The positive test now explicitly constructs that private ACL on its own new fixture directory before launching the child with missing module discovery. The unrelated-reader test remains unchanged and still requires rejection. Both controls pass locally. This is a fixture correction; it does not weaken the production policy or establish the original hosted failure's detailed ACL contents.
