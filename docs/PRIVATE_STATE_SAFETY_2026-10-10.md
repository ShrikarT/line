# Private-state safety remediation — 10 October 2026

This increment addresses the local vault portions of historical findings F10/F11 and advances PD-10. It does not close the full custody or recovery requirement. Compact and its twelve circuit bodies are unchanged in this increment.

## Implemented behavior

- Automatic expiry, manual locking and session replacement synchronously revoke the store's decrypted identities, credit openings, quotes, notes, repayments and private views. Every privileged console action checks the live session again immediately before invoking the runtime. Public ledger queries remain available.
- Session revisions prevent a late decrypt/save result from restoring a locked or superseded session. If an already-submitted operation reports success after locking, the store uses its captured opening and passphrase to save encrypted recovery records; it does not publish those private records to the locked UI. This is deliberately different from permitting a new operation after locking.
- The private-state provider has no plaintext read cache. State and signing-key methods require authorization, including deletion and prefix clearing. A browser password callback cannot bypass a locked vault. Standalone Node password callbacks remain supported.
- The versioned vault codec preserves nested `Uint8Array`, `bigint` including the full Uint64 range, optional `undefined` fields and ordinary JSON values. Tagged application objects cannot impersonate codec values. Invalid nodes, cycles, unsupported objects and accessors fail explicitly.
- New AES-GCM envelopes authenticate their record ID as additional data. Loads also check that the stored envelope ID matches the requested key. Existing unversioned ciphertext and ordinary JSON remain readable; legacy ciphertext did not authenticate the ID, and this compatibility path cannot establish retrospective identity binding or recover byte arrays already serialized incorrectly.
- IndexedDB promises resolve only after transaction completion, and aborted/error transactions reject. Authorization guards run after encryption/database opening and before mutation. Guarded transactions abort when a lock invalidates their authorization; cursor deletion rechecks the guard. Connections close after completion/failure.
- Browser storage unavailability fails closed. The provider's explicit optional fallback contains encrypted envelopes only, is volatile and is cleared on locking/disposal. Authentication, malformed payload and codec failures never activate fallback. A failed delete does not hide a remaining durable record. The non-browser vault's encrypted test store is cleared by `clearVaultState`; it is not durable CLI storage.
- Runtime-created private stores use the connected wallet's public coin key as account scope, in addition to network/contract/private-state scopes. The browser vault provider is disposed on wallet replacement/detachment or clearing the contract. Explicit default callers retain the legacy namespace, but key segments are now escaped; legacy IDs containing delimiters and accountless records need explicit migration. Runtime account scopes do not silently adopt legacy accountless records.
- Issued agent openings cannot be replaced through identity generation/import or direct zeroed identity saves. Rejected draws use **"Clearance could not be proven."**

## Evidence and limits

Regression coverage lives in `src/lib/security/vault.test.ts`, `src/app/store.test.ts`, `tests/vault-provider.test.ts`, `tests/network-sdk.test.ts` and the browser vault tests. The store tests exercise real model transitions and a confirmed draw returning after locking. Provider tests use real WebCrypto and barriers around encryption/decryption rather than treating a mocked cache as recovery evidence. IndexedDB transaction failure tests distinguish request success from commit, including a real lock after request success that aborts a provider write and preserves the previous opening. The legacy app test now creates actual console identities and a line through the UI, requires populated `line_vault_db/encrypted_keys` records and fails missing/error storage; it no longer inspects an unrelated empty database as privacy evidence. Navigation also rejects all page errors. See [engineering status](ENGINEERING_STATUS.md) for final run counts.

These checks establish the tested local behaviors. They do not establish resistance to a compromised browser/same-origin script, secure memory erasure by JavaScript, rollback resistance, institutional custody, independent role secrets, encrypted backup/restore, cross-process concurrency, or durable intent recovery after process crash and ambiguous network confirmation.

The legacy console still uses a shared multi-role store and one merchant identity; its books are scoped by network/contract, while the SDK provider now additionally uses wallet account scope. SDK account separation does not establish console role isolation. Its agent-line metadata records the generation observed before opening; metadata reconciliation needs to be included in durable operation recovery. Confirmed results can still be lost if the process dies before saving, or partially persisted across several records. Captured credentials may remain reachable by already-running asynchronous work until it completes; UI revocation is not a guarantee that all JavaScript memory is zeroed. These remaining requirements stay open under PD-02/06/10/13.
