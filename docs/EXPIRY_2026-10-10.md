# Ledger-time expiry and merchant deadline remediation

Date: 10 October 2026. This advances PD-08 and PD-13 while retaining all eighteen product requirements.

## Implemented behavior

The former monetary validity checks compared deadlines against a counter incremented by every successful operation. An issuer could accelerate expiry with unrelated activity. All validity checks now use supported Compact `blockTimeLt` predicates and permissionless cancellation uses `blockTimeGte`. Values are absolute seconds since the Unix epoch. Equality is expired. `actionClock` remains diagnostic ordering; no expiry decision reads it.

The merchant's authenticated quote fixes the resulting note deadline. `draw` requires `noteExpiry == quote.expiry`; an agent cannot shorten or extend that window. The same public expiry remains bound into the quote and private note opening. Facility, quote, note and repayment validity are checked at execution. No extra exported circuit or timestamp witness was added; twelve circuits/twenty witness interfaces remain.

The compiler required explicit disclosure of exported deadline arguments passed to block-time comparison. Deadlines/time bounds are public; the private limit/debt/remaining capacity are not newly disclosed by those arguments. Existing amount/history and zero-debt-closure leakage still applies. [Privacy boundary](PRIVACY.md).

Midnight documents local-machine time during DApp construction and approximate block time during on-chain state updates. A transaction constructed before a deadline can fail after proving/propagation. Real network time/finality acceptance remains unconfirmed; submit with an appropriate margin and reconcile actual receipts. This change establishes supported compiling constraints and local tests, not a guarantee of timely payout. [Official block-time semantics](https://docs.midnight.network/relnotes/compact/compact-0-17-25-0).

## Application and migration

- Console, MCP, smoke and generated checkout deadline creation uses current Unix seconds rather than activity counts. The checkout quote/claim window is 600 seconds; its facility deadline is 10,000 seconds. Existing console defaults use 10,000 seconds. They are development defaults, not commercially negotiated terms.
- The reference model keeps its injectable trusted clock outside public ledger state in a WeakMap and preserves it across model clones. Generated execution supplies trusted runtime context. Defaults use real Unix time. Explicit deterministic fixture clocks do not alter the production defaults or become caller-supplied witnesses.
- Transfer formats are now `line:quote-package:v2` and `line:note-package:v2`, with required `deadlineUnits: "unix-seconds"`. V1, missing units and unsafe numeric expiry values reject before import.
- Checkout snapshots are version 2 and require the same units. Persisted source fingerprints reject older journals/checkpoints. MCP development state rejects missing or action-count units with explicit fixture reset guidance. No old deadline, commitment, book or deployment was silently relabelled or migrated.
- Merchant and agent consoles show the agreed deadline in UTC. Merchant status reflects the recorded claim state; confirmed redeemed claims cannot be submitted again from that button.
- Internal page navigation now uses browser history without reloading the application. Console session, runtime and confirmed claim state survive role switches and back/forward. Explicit reload still has the separately documented runtime/custody recovery limitations. Checkout component unmount/reload still loses its browser capabilities; this navigation fix does not establish independent custody or durable checkout-client recovery.

## Remaining requirements

Compensation, refund/dispute decisions, borrower principal/fee reversal and actual cash-return liabilities are not implemented by cancellation. A payment assertion remains issuer supplied. Fee policy is still caller selectable; pending-versus-earned/refundable fees need exact accounting. A merchant deadline shared with quote acceptance does not promise a minimum post-acceptance interval; separate agreed acceptance/redemption windows and practical submission margins remain a product-policy dependency. Live chain time/finality, actual payouts, independent custody, full-history privacy and external supplier/customer evidence are still open. Old deployed contracts and records need deliberate verified migration, not marker changes.
