# Supplier runtime and wallet proving

This increment removes the supplier runtime's dependency on historical operator
facilities. It is runtime preparation, not a public deployment or a funded
organization acceptance result.

## Supplier custody

`server/organization-wallet.mjs` derives only the supplier fee wallet and two
supplier identities from `MIDNIGHT_SUPPLIER_MNEMONIC`. It does not derive an
organization issuer or agent role. It requires `LINE_SUPPLIER_DATA_DIR`,
`MIDNIGHT_STORAGE_PASSWORD` and the Preprod provider configuration. Its encrypted
wallet snapshot has an identity-bound process lease. Storage is acquired before
native wallet startup, and a failed stop retains ownership. A failed snapshot
write blocks further mutation. The storage password is captured when custody is
acquired; changing environment configuration does not silently rotate it.

The supplier controller uses the actual encrypted SDK LevelDB provider under
the same dedicated data directory. Signed bytes and public operation metadata
remain in the durable transaction journal. The journal is shared with the
historical runtime without loading its facilities, keys or cache files. Exact
signed uncertainty and independent receipt checks retain their existing rules.

The service serializes quote, redemption and pending recovery. Closing it denies
new work and drains the admitted operation before stopping the wallet and
releasing its lease. An independently opened service owns its parent wallet;
the local development service continues to share its existing parent.

The deterministic supplier profile is **new**. Its role keys and receiving
addresses are not the historical suppliers' randomly generated keys. Existing
organizations must retain their original supplier service for its outstanding
obligations; this factory is not a migration or a way to replace registered
recipients. No legacy receiving seeds have been discarded or moved.

## Organization proving

Browser organization transactions now acquire the connected wallet's
`getProvingProvider` lazily and use the installed Midnight.js `createProofProvider`
adapter. Public proving keys are supplied through the existing release-backed
key provider. The organization path no longer selects a first-party HTTP prover
or assumes a prover running on the user's localhost. Unsupported, declined or
unresponsive wallet proving returns an actionable failure before submission.
Acquisition and proving have explicit observation bounds; late resolution cannot
resume the awaiting transaction caller.

This follows the [Connector specification's proving interface](https://github.com/midnightntwrk/midnight-dapp-connector-api/blob/main/docs/api/_media/SPECIFICATION.md).
The wallet's chosen prover can learn proof preimages. Wallet delegation therefore
does not establish confidentiality against that prover or full-history privacy.
The supplier's own proofs still use its configured backend proof service.

## Verification and limits

Seven focused storage/lifecycle tests pass using actual HD derivation,
encrypted files, process leases and encrypted SDK controller reopen. They do not
start a funded wallet or make network submissions. One pauses an actual quote at
inspection and confirms closing cannot release custody until it settles.

The actual SDK maintenance test passes through the new wallet proving adapter,
constructs/signs/proves the maintenance transaction, then deliberately rejects
wallet balancing. It confirms zero submissions and no late continuation after
provider-acquisition timeout. This is adapter/encoding evidence, not an extension
approval or a circuit proof generated by Lace.

A separate random, empty wallet's actual native synchronization attempt timed
out after the 180-second synchronization bound; cleanup completed and the
process exited. It submitted nothing. Read-only provider probes subsequently
returned HTTP 200 with GraphQL data, accepted a WebSocket handshake and delivered
a DUST event through the native WebSocket implementation. Those probes narrow
the failure to the full sync path; they do not prove synchronization or funding.

The full current core run passes 605 of 606 discovered cases with one intentional
skip and no failures/cancellations. All eight organization browser cases pass;
desktop and phone creation both acquire a wallet prover, then reach the
deliberately rejecting connector with no submission. `build:deploy`, typecheck,
both Compact regenerations with zero managed drift and both credential scans
pass. The browser production graph contains 86 inspected modules. The actual
release export contains 37 public files. Both review axes accepted the shutdown
fix with no further actionable finding in this increment.

Still required: verified first-start synchronization and funded fee balancing;
authenticated production HTTP admission and network routing; persistent hosting,
restart and public browser acceptance; a new organization's complete funded
Preprod lifecycle; and the authorized privacy redesign. The owner is unavailable
to retry Lace now, so independent work continues without treating that as a
request to reduce scope.
