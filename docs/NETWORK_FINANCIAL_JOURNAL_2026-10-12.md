# Network financial journal boundary — 12 October 2026

The financial journal previously accepted `preprod` as a scope while its `initialize` and `confirm` methods trusted caller-supplied public state. Those methods now work only for `synthetic-preview`. A separate Preprod lane obtains finalized evidence internally through the read-only receipt reader. No new deployment, wallet balancing, transaction submission or asset transfer is claimed.

## Network lifecycle

The owner supplies a network authority at journal opening: matching network/source/executable identifiers, configured HTTPS indexer/RPC services and the exact twelve expected verifier keys. Keys and service settings are copied. Public service locations and verifier-key hashes become immutable authenticated namespace policy; credentials remain in memory. The source/key mapping is owner-pinned configuration, not an independent attestation derived merely from those hash strings. The actual deployment and compiled artifact provenance must be established before provisioning this authority.

1. `initializeFinalized(initial, anchor)` fetches the anchor receipt internally. It checks canonical finality, raw action/identifier integrity, exact saved intent bytes, the full verifier inventory and keys, and the expected public data before recording the initial checkpoint. A caller's success flag or copied state cannot bootstrap a network journal.
2. `prepare` persists the authorized candidate as before. `stageSubmission(operationId, transaction)` durably binds that candidate to exact final transaction bytes, identifiers, hash and circuit before dispatch. The application must call this after proof/signing/balancing and await successful publication before submitting. This method records intent; it does not submit or assert that an asset transfer occurred.
3. `confirmFinalized(operationId)` queries by the saved identifier. The reader discovers the actual included block and transaction hash, checks complete success and canonical finality, and verifies the encoded target action. Every saved identifier and bound intent must survive unchanged. The final public data and all verifier keys must match the saved candidate and owner policy before the checkpoint advances atomically.
4. Failures retain the candidate and submitted bytes. A completed retry returns the original persisted receipt without creating another liability. An optional block-height hint must agree; supplied states, arbitrary receipt objects and alternate transaction hashes are not accepted as confirmation authority.

Midnight can merge transactions: the enclosing finalized transaction hash may change while saved intent identifiers and bytes survive. The pinned SDK's `Transaction.identifiers()`, `Intent.serialize()`, `Transaction.merge()` and indexer `TransactionOffset.identifier` support this distinction. The journal accepts the tested merge form and records both submitted and finalized transaction hashes. It rejects altered saved proof/intent bytes even when a provider still reports success and the identifier remains the same. Arbitrary rebinding or replacement is not accepted.

Same-process reconciliation and publication exclude competing mutations. Closing during a receipt query prevents its later checkpoint write. Closing during an already-started encrypted publication waits for that write before releasing the writer lease. Publication failure makes the instance unavailable until reopening and reconciliation. This is not a power-loss guarantee or an external anti-rollback anchor.

## Compatibility and scope

Existing synthetic journal namespaces and methods remain compatible. Network policy changes require an explicit migration; older Preprod records created under the caller-trusted namespace cannot silently reopen as authenticated network records. No migration certifying those historical records is provided.

`scripts/private-finance-network.mjs` contains the network authority; `scripts/private-finance-journal.mjs` owns the durable lifecycle. The financial worker still initializes a synthetic scope and does not expose a live submission/balancing adapter. A manually supplied Preprod worker scope cannot fall back to bare-state confirmation: opening requires owner network authority, and the synthetic `confirm` method rejects it. Completing the actual worker/wallet/deployment integration remains required.

The authority trusts the configured TLS indexer/RPC and owner-pinned verifier set. It does not implement a light-client inclusion proof, independent full node, new cryptographic construction review or local verification of every network proof. Private checkpoint openings remain the authorized owner's responsibility; matching a public state alone does not certify every private opening. Authentic deposits, payout, fulfillment, repayment and refunds remain separate gates.
